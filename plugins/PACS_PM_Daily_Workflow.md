## 一、角色定位与核心职责

PACS 产品经理处于**医疗信息化**与**临床需求**的交叉点，需同时掌握以下四个维度：

| 维度 | 核心内容 |
|------|----------|
| **技术维度** | DICOM 3.0 标准、HL7 v2/FHIR、IHE 规范、影像重建算法基础 |
| **业务维度** | 放射科工作流、影像诊断流程、医院 HIS/EMR/LIS 对接 |
| **合规维度** | NMPA 医疗器械软件注册、二类/三类器械管理、等保 2.0 |
| **商业维度** | 招投标规则、医院预算周期、竞品格局、SaaS/私有化部署模式 |

### 1.1 核心职责清单

- 制定并维护 PACS/RIS 产品路线图（季度/年度）
- 采集、分析、优先级排序来自医院客户、销售、监管的需求
- 输出高质量 PRD（含 DICOM Tag 映射、HL7 消息规范、验收标准）
- 推动研发、QA、UE 多团队协同，保障版本按时高质量交付
- 组织放射科用户访谈、可用性测试，持续优化产品体验
- 评估功能变更对 NMPA 注册的影响，参与合规文件编制
- 支持售前技术答标，提供竞品应对策略

## 三、关键工作流程详述

### 流程 1：需求全生命周期管理

#### 1.1 需求来源采集

```
需求输入渠道
  ├── 客户工单         → JIRA/CRM 系统，按优先级标记
  ├── 医院现场反馈     → 季度巡场记录表，实施顾问收集
  ├── 销售商机需求     → 售前沟通纪要，按项目金额加权
  ├── 行业标准更新     → DICOM/HL7/IHE 变更公告订阅
  ├── 监管政策要求     → NMPA 公告、医保局文件、等保规范
  └── 竞品功能分析     → 月度竞品报告，主要对标厂商清单
```

#### 1.2 需求分析四步法

**Step 1 — 场景还原**
- 输出影像科实际操作流程图（BPMN 格式）
- 收集工作量数据（日检查量、高峰时段、并发用户数）
- 确认终端用户角色（医生/技师/护士/管理员）

**Step 2 — 优先级评估（RICE 模型）**

| 维度 | 评估要素 |
|------|----------|
| Reach（触达量） | 受影响的医院数量 × 科室用户数 |
| Impact（影响度） | 对核心业务流程的改善程度（1-5分） |
| Confidence（信心度） | 数据支撑充分度（%） |
| Effort（工作量） | 研发人天估算 |

> RICE Score = (Reach × Impact × Confidence) ÷ Effort

**Step 3 — 技术可行性评估**
- 联合架构师评估 DICOM SOP Class 支持范围
- 确认 HL7/FHIR 消息改造范围
- 评估对现有数据库结构的影响
- 确认第三方设备（DR/CT/MR）兼容性

**Step 4 — 合规性预审**
- 是否触发医疗器械软件重大版本变更
- 是否引入新的患者数据处理方式
- 是否需要更新 DICOM 一致性声明
- 是否影响网络安全边界

#### 1.3 PRD 产出标准

PRD 文档必须包含以下章节：

```
1. 背景与目标
   ├── 业务背景（数据支撑）
   ├── 用户故事（User Story 格式）
   └── 成功指标（可量化）

2. 功能规格
   ├── 用例图（Use Case Diagram）
   ├── 交互流程图（时序图/泳道图）
   ├── 界面原型（Axure/Figma 链接）
   ├── DICOM Tag 映射表（若涉及影像数据）
   └── 边界条件与异常处理

3. 接口规范
   ├── HL7 消息样例（ORM/ORU/ADT）
   ├── FHIR 资源定义（若适用）
   ├── REST API 设计（若涉及新接口）
   └── 第三方设备集成说明

4. 非功能需求
   ├── 性能指标（响应时间/并发数）
   ├── 安全要求（访问控制/加密/审计）
   └── 兼容性要求（OS/浏览器/工作站型号）

5. 验收标准
   ├── Gherkin 格式用例（Given/When/Then）
   └── 测试数据准备说明

6. 合规影响说明
   ├── 软件版本变更类型判定
   └── 所需更新的注册文件清单
```

### 流程 2：迭代版本管理

#### 2.1 版本发布节奏

| 版本类型 | 周期 | 内容范围 | 合规要求 |
|----------|------|----------|----------|
| 大版本（X.0） | 年度 | 架构升级、核心功能重构 | 变更注册/重新注册 |
| 中版本（X.Y） | 季度 | 新功能模块、重要优化 | 变更评估，按需申报 |
| 补丁版本（X.Y.Z） | 月度 | 缺陷修复、安全补丁 | 变更控制记录 |

#### 2.2 Sprint 迭代流程（2周/Sprint）

```
Sprint 规划（第1天）
  ├── 产品 Backlog 梳理（PD 主导）
  ├── Story Point 估算（开发团队）
  ├── Sprint Goal 确认
  └── 任务分配到人

开发迭代（第2-8天）
  ├── 每日站会（15 min）
  ├── 需求澄清（PD 响应时间 < 2h）
  ├── 设计评审（中期，第3-4天）
  └── 代码 Review（研发自管理）

测试阶段（第9-12天）
  ├── QA 功能测试
  ├── PD 验收测试（按 Gherkin 用例）
  ├── DICOM 兼容性专项测试
  └── 性能压测（大版本必须）

Sprint 收尾（第13-14天）
  ├── Sprint Review（功能演示给相关方）
  ├── Sprint 回顾（四象限复盘）
  └── 发布决策（PD 签发 Go/No-Go）
```

#### 2.3 发版检查清单

```
上线前必检项（PD 负责确认）
  ├── □ 医疗器械软件变更评估表（已完成并存档）
  ├── □ 网络安全评估报告（含等保条款核查）
  ├── □ 兼容性测试报告
  │     ├── 主流影像工作站（Lenovo/HP/戴尔）
  │     ├── 主流浏览器（Chrome/Edge，最新两版本）
  │     └── 移动端（iOS 15+/Android 10+，若有）
  ├── □ DICOM 一致性声明更新（若涉及 DICOM 变更）
  ├── □ 用户操作手册变更章节（版本号同步更新）
  ├── □ 客服/实施培训材料（新功能操作说明）
  ├── □ 数据迁移脚本测试（若涉及数据库结构变更）
  └── □ 回滚方案确认（紧急回滚步骤文档化）
```

### 流程 3：用户研究流程

#### 3.1 定性研究（每月执行）

**访谈对象分层**

| 角色 | 访谈重点 | 每月频次 |
|------|----------|----------|
| 影像科主任 | 科室效率指标、管理痛点、采购决策因素 | 1次 |
| 放射科医生 | 诊断工作流、报告效率、AI 辅助体验 | 2次 |
| 放射技师 | 设备操作流程、图像质控、摆位辅助 | 1次 |
| 医院 IT 管理员 | 系统集成痛点、运维成本、安全合规需求 | 1次 |
| 实施顾问 | 客户高频问题、上线阻力、竞品对比 | 1次 |

**访谈执行标准**

```
访谈前准备
  ├── 阅读客户历史工单和 NPS 评分
  ├── 准备访谈提纲（问题不超过 10 个）
  ├── 确认录音/录屏授权
  └── 准备原型演示素材（若需验证）

访谈结构（60 min）
  ├── 破冰与背景了解（10 min）
  │     └── 岗位、工作量、典型工作日描述
  ├── 当前流程走查（20 min）
  │     └── 要求用户操作系统，观察实际行为
  ├── 痛点深挖（15 min）
  │     └── 5WHY 追问法，不接受表面答案
  ├── 新功能原型验证（10 min）
  │     └── 任务场景测试，记录完成率与困惑点
  └── 竞品使用情况（5 min）
        └── 是否使用其他系统，优势在哪

访谈后输出（24h内完成）
  ├── 访谈纪要（关键引语原文保留）
  ├── 痛点卡片（一个痛点一张卡）
  └── 需求反推（用户痛点 → 产品需求）
```

**月度输出物**
- 用户故事地图（User Story Map）更新版
- 痛点热力图（按频次和严重度双维度）
- 新增需求入池（标注来源和置信度）

#### 3.2 定量研究（持续监控）

```
埋点数据监控（每周分析）
  ├── 功能模块使用率（MAU/DAU 分功能统计）
  ├── 关键任务完成率（报告生成、图像调阅）
  ├── 平均任务时长（关键操作路径耗时）
  ├── 错误率与错误类型分布
  └── 功能弃用率（用户放弃操作的节点）

NPS 调研（每季度）
  ├── 推送时机：版本上线后 30 天
  ├── 问卷结构：NPS 主题 + 3 个开放题
  ├── 目标回收率：> 30%
  └── 分析输出：按科室/角色/医院等级分层

客服工单分析（每月）
  ├── Top 10 问题类别 + 频次趋势
  ├── P1/P2 缺陷根因分析
  ├── 平均解决时长（SLA 达标率）
  └── 产品 vs. 操作问题占比（指导培训方向）
```

#### 4.2 需求变更控制

```
变更申请触发条件
  ├── Sprint 进行中客户紧急需求
  ├── 监管政策变更（强制合规）
  └── 重大缺陷影响核心流程

变更评估流程
  1. 提交变更申请（说明影响范围和紧急程度）
  2. PD 评估影响：工作量/Sprint 目标/发版计划
  3. 三方确认：PD + 研发负责人 + 业务方
  4. 决策：纳入当前 Sprint / 排入下个 Sprint / 拒绝
  5. 存档变更记录（含决策理由）
```

### 流程 5：医疗合规流程（NMPA）

#### 5.1 软件变更类型判定

根据 **YY/T 0664** 标准，软件变更分为：

| 变更类型 | 判定标准 | 处置方式 |
|----------|----------|----------|
| 重大软件版本 | 新增临床功能、修改核心算法、扩展预期用途 | 变更注册申请 |
| 次要软件版本 | 性能优化、非核心模块改动、UI 优化 | 技术文件更新存档 |
| 维护版本 | 缺陷修复、安全补丁 | 变更控制程序记录 |

**高风险变更场景（必须合规评估）**

```
├── 新增 AI 辅助诊断功能          → 可能触发三类器械重新注册
├── 修改图像重建/后处理核心算法    → 变更注册 + 性能测试报告
├── 新增患者数据传输接口           → 网络安全文档更新
├── 扩展至新影像模态（如核医学）   → 预期用途变更
└── 与第三方 AI 平台深度集成       → 独立软件组件评估
```

#### 5.2 注册准备文件清单

```
基础注册文件（常备更新）
  ├── 软件描述文档（SDD）
  │     ├── 软件架构描述
  │     ├── 核心功能模块说明
  │     ├── 数据流图
  │     └── 第三方组件清单（含版本号和开源协议）
  ├── 网络安全描述文档
  │     ├── 资产清单与威胁分析
  │     ├── 安全控制措施
  │     └── 漏洞管理程序
  ├── 软件版本控制文档
  │     ├── 版本命名规则
  │     ├── 变更历史记录
  │     └── 配置管理说明
  └── 剩余风险评估报告（ISO 14971）

三类器械附加文件
  ├── 临床评价报告
  ├── 算法验证报告（含测试数据集说明）
  └── 上市后监督计划
```

#### 5.3 DICOM 一致性声明维护

```
触发更新场景
  ├── 新增支持的 SOP Class（如 SR/KOS/GSPS）
  ├── 修改现有 SOP Class 的必选 Tag 处理逻辑
  ├── 新增支持的影像设备品牌/型号
  └── 修改传输语法（Transfer Syntax）支持列表

更新流程
  1. 研发列出变更的 DICOM 功能清单
  2. PD 确认对应 Conformance Statement 章节
  3. 专业 DICOM 工程师完成文档修订
  4. DICOM 验证工具（DCM4CHE/OsiriX）回归测试
  5. 文档版本同步至官网和注册文件
```

## 五、关键指标体系（OKR/KPI）

### 5.1 产品质量指标

## 六、行业特殊注意事项

### 6.1 DICOM 标准合规

```
基础要求
  ├── 每个影像相关功能必须对应 DICOM 一致性声明条目
  ├── DICOM Tag 处理规则需文档化（必选/可选/私有Tag）
  └── 私有 Tag 使用需与主流影像设备厂商协商确认

高风险 SOP Class（需专项测试）
  ├── Structured Report (SR)    → 报告对象，结构复杂
  ├── Key Object Selection (KOS) → 关键图像标记
  ├── Grayscale Softcopy PS (GSPS) → 显示状态保存
  ├── RT 系列                   → 放疗计划相关（高风险）
  └── Worklist (MWL)            → 检查预约单，HIS 对接核心

多模态兼容测试矩阵（必须覆盖）
  ├── CT（螺旋/平扫/增强）
  ├── MR（多序列：T1/T2/DWI/MRCP）
  ├── DR/CR（数字放射摄影）
  ├── DSA（数字减影血管造影）
  ├── 超声（二维/彩超/三维）
  └── PET/CT、核医学（SPECT）
```

### 6.2 HL7/FHIR 集成注意事项

```
HL7 v2 核心消息（与 HIS/RIS 对接）
  ├── ORM^O01  → 检查申请单（HIS → RIS）
  ├── ORU^R01  → 检查报告回传（RIS → HIS）
  ├── ADT^A01  → 患者入院/信息更新
  └── SIU^S12  → 预约排班消息

常见集成风险
  ├── 字段编码不一致（科室代码/医生工号映射）
  ├── 字符集问题（中文 GBK vs. UTF-8）
  ├── 时间格式不统一（影响工作列表排序）
  └── 大量级压测（高峰期消息堆积处理）

FHIR 适配方向（互联网医院/区域影像）
  ├── ImagingStudy 资源（检查记录）
  ├── DiagnosticReport 资源（诊断报告）
  └── Patient/Practitioner 资源（基础数据）
```

### 6.3 安全合规要求

```
等保 2.0 三级（公立三甲医院标准配置）
  ├── 身份认证：双因素认证/CA 证书
  ├── 访问控制：基于角色的权限模型（RBAC）
  ├── 安全审计：操作日志留存 ≥ 6 个月
  ├── 数据加密：传输层 TLS 1.2+，存储加密（含磁盘级）
  └── 入侵防范：异常访问检测与告警

患者隐私保护（PHI 处理规范）
  ├── 影像数据不得离开院区（私有化部署原则）
  ├── 科研数据导出须经患者信息脱敏（DICOM Tag 清洗）
  ├── 系统日志不得记录完整患者 ID
  └── API 接口调用须实施身份验证与权限校验
```

### 6.4 采购周期与路线图匹配

```
公立医院政府采购节奏
  ├── 11月         → 次年预算锁定，需完成产品演示和立项
  ├── 12月-2月     → 招标文件编制期，功能清单需冻结
  ├── 3月-6月      → 招投标密集期，售前技术支持高峰
  └── 7月-9月      → 中标合同签署，实施项目启动

产品路线图节奏建议
  ├── 大功能发布窗口：9月-10月（赶在预算期前形成参考）
  ├── 招标关键词准备：配合销售提取竞争优势功能点
  └── 路线图发布对外时机：每年 9月（RSNA 前后）
```
